# 页面生成链路讲解

> 目标读者：第一次接触这个仓库的人。
> 读完应该能回答：一份后端 JSON 是怎么变成一个能增删改查的页面的？每一步发生在哪个文件？

## 先说大局

整个链路分成**两个阶段**，时间点不同，别混在一起：

1. **生成阶段**（你跑 `pnpm gen:pages` 时，在 Node 里发生）：把 JSON 变成 `.vue` 文件。
2. **运行阶段**（你跑 `pnpm dev`，浏览器里发生）：这些 `.vue` 文件被当成普通页面渲染、发请求。

组件库 `packages/ui`（ProTable 那套）属于运行阶段；`packages/page-generator` 全部是为了生成阶段服务的。

## 仓库里有什么

```
apps/demo                    # 演示应用：展示「JSON 渲染页面」的最终效果
apps/playground              # 组件演示站：仿 antdv 官网，固定演示二次封装组件的用法
packages/ui                  # 组件库：ant-design-vue 二次封装（ProTable / ProFormBuilder / openDialog / createApis）
packages/page-generator      # 生成器：拉 JSON → 拼 vue 字符串 → 写文件
scripts/mock-server          # 模拟后端：页面登记文档接口 + 各页面 CRUD 数据
```

三个前端应用的分工：

- **demo**（`pnpm dev`）：演示「页面是生成出来的」。它自己不写页面代码，页面全在 `src/pages/` 下由脚本生成。
- **playground**（`pnpm dev:playground`）：演示「组件怎么用」。页面是手写的、固定的，类似 ant-design-vue 官网的每个组件文档页。
- **mock-server**（`pnpm mock`）：不是前端应用，是给上面两个提供数据的假后端。

## 生成阶段：JSON 怎么变成 vue 文件

### 第 1 站：后端把 JSON 登记在文档上

这一步是后端的事，仓库里用 `scripts/mock-server/server.mjs` 模拟。它提供一个公开的查询接口：

```
GET http://localhost:4173/api/page-registry
```

返回的内容大意：

```json
{
  "version": "2026-09-08",
  "pages": [
    {
      "route": "/users",
      "name": "UsersPage",
      "title": "用户管理",
      "api": "/api/users",
      "columns": [{ "title": "姓名", "dataIndex": "name" }],
      "formItems": [{ "label": "姓名", "key": "name", "type": "input" }],
      "rules": { "name": [{ "required": true, "message": "请输入姓名" }] }
    }
  ]
}
```

注意这份 JSON 里**没有任何代码**，只有配置：路由叫什么、表格有哪些列、表单有哪些项、调哪个接口。这就是「后端登记的那份 JSON」。

### 第 2 站：脚本请求回这份数据

`pnpm gen:pages` 实际执行 `packages/page-generator/src/cli.mjs`。它先调 `fetchSchemas.mjs` 的 `loadPageSchemas()`，核心就是一句 `fetch(registryUrl)`，把上面的 JSON 拿到手。此时脚本手里有了「N 个页面」的配置数组。

### 第 3 站：把 JSON 组装成字符串

核心在 `packages/page-generator/src/generate.ts` 的 `generatePageSfc()`。它做的事没有任何魔法——用模板字符串拼出一段文本，这段文本恰好是一个合法的 `.vue` 文件内容：

```js
return `<script setup lang="ts">
import { ProTable, createApis } from '@snowbitx/ui'
...
const apis = createApis('${api}')     // ← JSON 里的 /api/users 填进来

const columns = ${columnsCode}        // ← JSON 里的 columns 数组展开填进来
const formItems = ${formItemsCode}    // ← JSON 里的 formItems 填进来
const rules = ${rulesCode}            // ← JSON 里的 rules 填进来
</script>

<template>
  <ProTable :apis="apis" :columns="columns" :form-items="formItems" :rules="rules" />
</template>`;
```

也就是说，生成的页面和你在 demo 里手写 `App.vue` 的写法一模一样（定义 columns、formItems，摆一个 ProTable），只不过这些常量的**值**是从 JSON 灌进去的。JSON 的每个字段在这里找到归宿：

| JSON 字段                  | 去向                                 |
| -------------------------- | ------------------------------------ |
| `columns`                  | 表格列（a-table columns）            |
| `formItems`                | 弹窗表单项（ProFormBuilder）           |
| `rules`                    | 表单校验（a-form rules）             |
| `api`                      | 这页数据的增删改查地址（createApis） |
| `route` / `name` / `title` | 路由和菜单                           |

### 第 4 站：字符串写进文件

`packages/page-generator/src/writer.mjs` 把字符串交给 prettier 按项目风格（无分号、单引号）格式化，然后写入：

- `apps/demo/src/pages/UsersPage.vue`（每个页面一个文件）
- `apps/demo/src/pages/index.ts`（路由注册表：一堆 import + `generatedRoutes` 数组）

生成阶段到此结束。**本质一句话：脚本替你手写了本该手写的页面文件。**

## 运行阶段：生成的文件怎么变成页面

### 第 5 站：路由接管

`apps/demo/src/router/index.ts` 里 `import { generatedRoutes } from '../pages'`，把生成的数组展开进路由表。后端 JSON 里登记了几个页面，这里就自动有几条路由——**新增页面不需要改路由代码，重跑一次脚本就行**。

### 第 6 站：界面壳子

`apps/demo/src/App.vue` 左侧读 `generatedRoutes` 画菜单，右侧 `<router-view>` 渲染当前页面。

### 第 7 站：页面自己跑起来

浏览器打开 `/users` 时渲染的就是生成的 `UsersPage.vue`，它内部做两件事：

1. `createApis('/api/users')`（组件库提供，`packages/ui/src/createApis/index.ts`）——把 api 地址包装成 ProTable 需要的 `get/create/update/remove` 四个方法（基于 fetch 的默认实现）。后端真实接口出来后只改这一个文件。
2. 渲染 `<ProTable>`——回到组件库：挂载时调 `apis.get()` 拉列表填表格；点「新增/修改」走 `openDialog` 弹出 `ProTableForm`，表单项按 `formItems` 由 `ProFormBuilder` 渲染，提交时调 `create/update`，点「删除」调 `remove`。

## 一句话串起来

> 后端在文档接口上登记一份 JSON（只有配置）→ `gen:pages` 脚本请求它，把配置灌进 vue 文件模板，写出 `.vue` 文件 → demo 的路由 import 这些文件 → 页面里 ProTable 拿着 JSON 给的接口地址和表单配置，跑起完整的增删改查。

下次后端想上线一个「订单管理」页面，他只是在文档里多登记一段 JSON，前端**一行代码不写**，`pnpm gen:pages && pnpm dev` 就多出一个能用的页面——这就是这套流程要演示的价值。

## playground 和这条链路的关系

playground（`apps/playground`）**不参与生成链路**，它是组件库的固定演示站，仿照 ant-design-vue 官网的形式：

- 每个组件一个文档页：ProTable / ProFormBuilder / openDialog；
- 每个页面由若干「案例块」（`DemoBlock`）组成：上面跑着真实组件，点「代码」能看到这段案例的源码（通过 vite 的 `?raw` 把案例文件源码原样展示，保证看到的代码就是跑着的代码）；
- 页面底部附 API 表格（Props / Expose / Slots）。

它的价值：改组件库的人可以随时打开 playground 回归组件行为，和「JSON 生成页面」的 demo 互不干扰。

## 常见疑问

**Q：为什么不直接在浏览器里用 JSON 动态渲染，而要生成 .vue 文件？**
生成文件的方式让页面成为仓库里真实存在的代码：能走类型检查、能被 IDE 跳转、能 code review、构建时静态打包。运行时动态渲染（比如用 `h()` 递归渲染 JSON）则灵活但丢失了这些工程化能力。本仓库演示的是前者。

**Q：JSON 变了要手动重新生成吗？**
是。`pnpm gen:pages` 是显式动作，适合后端登记后、发版前跑一次。要自动化可以把它挂进 CI。

**Q：生成的页面里能写特殊逻辑吗？**
生成物定位是「标准增删改查页」，保持简单。特殊页面就手写，放在 `src/views/` 下自己注册路由——和生成的页面可以共存。
